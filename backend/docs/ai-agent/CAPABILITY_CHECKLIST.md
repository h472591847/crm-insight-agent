# CRM 数据分析能力清单（2026-11-10 实际可统计）

> 用途：服务启动后手动做真实场景测试。本文只列**当前代码真实可用**的能力；凡是做不到的，都写了原因与替代做法。
>
> 数据来源：`member_info_view`（CRM 会员列表页同口径表，触发器同步物理表）、`expense_calendar_info`（订单头）、`expense_calendar_details`（消费明细）。所有金额均为订单实付。

## 一、实体与可用字段

说明：
- **PII**：个人信息列。可以用于过滤/计数，但**禁止原值输出**（不得列名单、不得当维度分组名展示，回答里不出现手机号/姓名）。
- **索引**：有索引的列过滤更快；无索引列过滤会扫会员表（428,930 行），可用但慢。
- **维度**：可分组统计；**过滤**：可作筛选条件；两者列表不一定相同（例如会员名可过滤但不可分组输出）。

## 二、支持的筛选写法（CRM 参数 → 本系统）

每条给一个可直接照念的自然语言提问示例。

### 1. 手机号（精确，禁止模糊）

> “查一下手机号 13153010172 这个会员的分配门店和要客状态。”

系统落：`member_mobile = '13153010172'` 等值过滤。**只支持完整号码精确匹配**；给部分号码会触发澄清或拒绝，不做前缀/包含匹配。

### 2. 姓名（模糊，PII 不出原值）

> “查姓名里含‘范成’的会员有多少个，按分配门店分一下。”

系统落：`member_name LIKE '%范成%'`。**只能返回数量/占比等聚合，不显示姓名**（重名命中多条，姓名不作为唯一标识）。

### 3. 要客 / PLUS / 分配状态

> “PLUS 会员里，已分配门店、是美团渠道的有多少？”

系统落：`plus_type='1' AND member_is_allot_store='1' AND channel_type='2'`，输出用 PLUS_TYPE / ALLOT_STORE_FLAG / CHANNEL_TYPE 维度。

> “我要客有多少？新增了多少？踢出了多少？”

系统落：`track='1'` 快照计数（VIP_OVERVIEW）；按 `track_time` 窗口计数（VIP_NEW）；按 `track_cancel_time` 非空计数（VIP_CANCELLED）。

> “要客里按导购 / 按门店 / 按性别 分别有多少？”

系统落：VIP_BY_STAFF / VIP_BY_STORE / VIP_BY_GENDER 分组指标。

### 4. 渠道

> “美团渠道的会员有多少？”

系统落：`channel_type='2'`（1=饿百 / 2=美团 / 3=京东到家）。注意：真库该列仅 25 行非空，过滤结果通常极小。**不支持 LIKE/IN，只支持 `=`、`!=`、`IS NULL`**。

### 5. 注册时间窗 / 最近消费时间窗

> “2026-11-02 到 2026-11-09 注册的会员有多少？”

系统落：`member_created` 落入 [开始, 结束+1天) 窗口（含结束日全天）。

> “最近一次消费在 2026-11-01 到 2026-11-08 之间的会员有多少？”

系统落：`reserved2 >= '2026-11-01' AND reserved2 < '2026-11-09'`（右开，不含结束日）。注意：这是“最近一次消费落在该区间”，**不等于“区间内有消费”**。

### 6. 金额区间（18 个月快照列，只筛人不当金额输出）

> “18 个月消费金额在 1000 到 4000 之间的会员有多少？”

系统落：`member_expense_totalsum_year >= 1000 AND member_expense_totalsum_year <= 4000`（闭区间，与 CRM 列表页 strMoney/endMoney 同列同口径）。**该列只用于筛人**；要输出金额（如“平均消费多少”）走订单实时汇总（见指标表），两者口径不等价，不得声称一致。

### 7. 各层级字段（单值）

> “公司级别是 AB 的会员有多少？” / “总销售级别是 DA 的会员有多少？”

系统落：`company_level='AB'` / `total_year_level='DA'` 等值过滤（级别是编码，原样输出）。

> “顾客价值是‘重要价值用户’的会员有多少？”

系统落：`customer_cost='重要价值用户'`（顾客价值直接存中文）。

### 8. 多值 IN（哪些列可用，上限 500）

> “顾客价值是重要价值用户或一般发展用户的会员有多少？”（对应 CRM `customerCost` 多值）

系统落：`customer_cost IN ('重要价值用户','一般发展用户')`。

> “公司级别是 AB 或 AC 的会员有多少？”

系统落：`company_level IN ('AB','AC')`。

可用 IN 的列：`member_allot_store`、`member_store`、`company_level`、`city_level`、`store_level`、`personal_level`、`half_year_level`、`total_year_level`、`customer_cost`、`new_member_level_value`、`reserved15`、`track`、`isAllotStaff` 等（见第一节“允许操作符”含 IN 的列）。

限制：
- 去重后 **最多 500 个值**，超出直接拒绝；
- 值含逗号也按一个完整值处理，不拆分；
- **手机号列禁止 IN**（保持仅精确匹配）；
- 同一列 `=` 与 `IN` 并存仍按 AND 叠加。

### 9. 门店范围（`member_allot_store IN`，配 resolveOfficeStores）

> “小酒喔总部下面的门店，PLUS 会员有多少？”（机构范围）

正确流程：先调 `resolveOfficeStores`（按机构 ID 或名称）→ 拿到门店编码数组 → 再查。
- 名称按"精确优先、逐级降级"：精确命中即直接解析下级门店（总部/大区等非门店类型也照常解析，不再追问）；只有降级后仍多候选才返回候选让你确认。
- `resolved`：把 `storeCodes` 传给 `member_allot_store IN (...)`。
- **总部级范围（369 店）在 500 上限内，可直接查**；只有机构下门店超过 500 时才拒绝并提示缩小范围，不截断、不分批。
- **门店类型口径：6/11/22/28（直营/加盟）**；**渠道店（18，非 8 位 HD_ID）不纳入统计**，要客部（13）、新媒体（14）同样排除。因此本系统口径比 CRM `getHDStationIDs` 少 6 个编码（375 → 369），这 6 个编码上会员数为 0，不影响会员统计。
- **门店名兜底**：`guessStation` 在会员表三级匹配全空时，会用机构表同口径（6/11/22/28、8 位 HD_ID）再匹配一次；唯一命中返回 `matchedBy=office_only`、`memberCount=0`、`hasOrders`，语义是"门店存在但当前没有会员分配记录"，**不得说成门店不存在**；渠道店仍返回 `no_match`。
- **历史会员口径差异**：18 个存活门店编码之外（机构表已无对应记录或已删除）的历史会员共 **2,504 人**，这些会员不会出现在任何机构/门店维度的范围统计中；按全库统计仍会计入。

**⚠️ 口径差异（重要）：当前系统无登录态，默认查询范围 = 全库；CRM 会员列表页默认范围 = 当前登录用户的机构范围（后端强制注入 `HDIDs`，不依赖前端选择）。** 要对齐 CRM 结果，请在提问时显式说"总部范围""小酒喔总部下"或具体机构名称；**未来接入登录后将自动对齐 CRM 权限范围**——由 `AdhocQueryService` 在入口强制注入当前用户权限内的 `member_allot_store IN (...)` 过滤（与模型显式指定的范围自动取交集，全局管理员豁免），改动点固定在服务层、不进 metadata.yaml 的 baselineFilters。

> “门店编码 04010112 和 04010113 的会员有多少？”

系统落：`member_allot_store IN ('04010112','04010113')`（≤500 时）。

## 三、明确不支持的部分（原因 + 替代做法）

| 场景 | 原因 | 替代做法 |
|---|---|---|
| 单个机构下门店超过 500 个 | IN 去重后上限 500；`resolveOfficeStores` 返回 `too_many_stores` | 缩小机构范围（选具体门店/更细下级机构）；不截断、不分批，防误用部分门店算错数 |
| IN 上限 500 | 参数化占位符与查询安全边界；总部级 369 店（已排除渠道店/要客部/新媒体）在上限内 | 超过 500 时缩小范围或多值分多次查 |
| 渠道店（type=18）不纳入门店统计 | 业务已确认渠道店不计入；其 HD_ID 非 8 位数字编码 | 统计门店范围时只算直营/加盟（6/11/22/28）；渠道店按名称查询返回"不纳入统计" |
| 多时间窗不能同时生效 | 单 `timeRange` 槽位 | 注册时间窗走 `member_created`；“最近消费时间”用 `reserved2` 两条过滤；消费区间统计走订单指标（另一次查询） |
| 聚合结果过滤（HAVING） | 引擎未实现“按会员聚合后落区间” | 金额区间用预聚合快照列 `member_expense_totalsum_year`（已支持，见 2.6）；实时聚合区间的 HAVING 待开发 |
| 商品名过滤 | `expense_d_commName` 未开放为过滤列（CRM 用 MATCH…AGAINST 需全文索引，其他报表用 LIKE，口径不统一） | 商品名**仅可作分组维度**；按类别名 `expense_d_commCodeName` 过滤；或先按 SKU 精确过滤 |
| 电话回访（answerVisit / answerVisitBegin/End） | 回访明细在 `access_record_info` 表，未接入本项目数据模型；CRM 自身对 answerVisitBegin/End 也未实现 | 暂无法统计“本月有电话回访的会员”；回访相关等后续接入 |
| `office_id` 不能代替门店范围 | `member_info.office_id` 与分配门店 `member_allot_store`（HD_ID）不是同一字段 | 必须走 `resolveOfficeStores` 拿门店编码再 IN |
| 姓名 LIKE 前导 `%` 用不上索引 | `%范成%` 无法走 index_name 前缀匹配 | 可接受（会员表 43 万行一次扫描）；回答里只出聚合不出姓名 |
| `channel_type` 真库仅 25 行非空 | 会员视图该列几乎为空（渠道主要在订单/明细侧） | 渠道过滤结果极小属正常；按订单侧渠道统计暂不可用 |
| 金额口径：订单实时 vs CRM 快照 | CRM 列表页金额区间用 18 个月快照（非实时、快照子查询未加 `expense_state='10'`，可能含已退单金额）；我们用订单实付实时汇总 | 两者**不等价**；筛人选快照列，算金额走订单实时汇总；回答里不得声称两者一致 |

| VIP_NEW | 新增要客数 | 按 track_time 窗口计数 | member_info_view | ✅ 门店过滤 |
| VIP_CANCELLED | 踢出要客数 | track_cancel_time 非空计数 | member_info_view | ✅ 门店过滤 |
| VIP_BY_STAFF | 按导购统计要客数 | track=1 按负责导购分组 | member_info_view | ✅ 纯会员 |
| VIP_BY_STORE | 按门店统计要客数 | track=1 按分配门店分组 | member_info_view | ✅ 纯会员 |
| VIP_CONSUMPTION_BY_STORE | 按门店统计要客消费 | 要客（track=1）的订单实付汇总 | order + member join | ✅ 会员分配门店 |
| VIP_BY_GENDER | 按性别统计要客数 | track=1 按性别分组 | member_info_view | ✅ 纯会员 |
| STATION_SALES | 门店销售业绩 | 订单实付汇总 + 订单数 + 客单价 | order | ⚠️ 只有门店维度 |
| PRODUCT_RANKING | 商品销售排行 | 明细行按 SKU 聚合实付/销量 | detail | ⚠️ 只有门店维度；时间窗≤92天 |
| GENDER_CONSUMPTION_COMPARE | 男女消费对比 | 订单头按会员性别分组对比销售额 | order + member join | ✅ 会员性别 |

说明：
- “可交叉会员属性”= 能否在同一个查询里既按会员维度（分配门店/性别/要客/级别等）分组又统计该指标。
  - **✅ 纯会员/可交叉**：可以。
  - **⚠️ 只有门店维度**：订单/明细类指标只能按门店分组（STATION），不能按会员性别/级别/要客等交叉；要交叉需走 adhoc 查询（主表 order/detail + member join）。
- 通用 adhoc 查询（`adhocQuery`）不占用上述指标，可自由组合第一节的维度/过滤/度量（金额度量一律订单实付）。
